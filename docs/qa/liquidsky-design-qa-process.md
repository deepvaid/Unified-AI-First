# LiquidSky design QA — process and reference

Status: **proposal** (2026-11-10). Scope: the LiquidSky components currently in design review.

## The problem

- Design review is a serial gate in front of QA, with one reviewer.
- The review criteria are generic. Nothing in them is measurable, so a developer cannot self-check
  and QA cannot assert.
- Findings are not recorded in one place, so nobody can see which kinds of feedback repeat.
- There are two Storybooks with two vocabularies and no map between them: the reference (`Mp*`,
  this repo) and the implementation (`App*`, LiquidSky).

## What "source of truth" means without Figma

A screenshot of an `Mp*` story cannot be pixel-compared with an `App*` component: the DOM, the sample
content and the story frame all differ. So the reference is split in two.

| | Comes from | Used for |
|---|---|---|
| **Spec contract** | This repo — `public/qa-reference/spec/<component>.json` | Numbers per part (padding, radius, colour, font). Asserted with Playwright `toHaveCSS`. Implementation-independent. |
| **Visual reference** | This repo — `public/qa-reference/png/…` | What it should look like, per state and theme. Compared by eye, side by side. |
| **Pixel baseline** | LiquidSky's own Storybook | Captured at design sign-off. Catches unintended change from then on (`toHaveScreenshot` or Chromatic). |

Design approval *creates* the pixel baseline. It is never produced by the design team in advance.

Both reference sets are generated by `npm run qa:export` and served from the deploy at
`/qa-reference/manifest.json`. In Storybook the same data is at **Foundations › QA Reference**.

## Workflow

1. **Dev self-check.** Before requesting review the developer opens the paired `Mp*` story (from the
   component map), runs the spec assertions against their own story and pastes the result in the
   ticket. No evidence, no review.
2. **Parallel tracks.** The story moves to QA as soon as dev is done. Functional QA and design
   review run at the same time. Neither waits for the other.
3. **Findings on the review ticket**, one line each:
   `part · expected (token / value) · actual · screenshot · severity`.
4. **Severity decides what blocks.**

   | Label | Meaning | Effect |
   |---|---|---|
   | `design-blocker` | Wrong component, a broken or missing state, an accessibility failure | Holds the release |
   | `design-must-fix` | A value that does not match the spec contract | Fixed in the same sprint; does not hold QA |
   | `design-polish` | Subjective or not covered by the spec | Backlog |

5. **Sign-off = baseline.** When the review is closed, QA captures the LiquidSky story as the pixel
   baseline. Changing a baseline later needs a designer's OK on the ticket.
6. **Review cadence.** Two fixed 30-minute batch slots a week; 2 working days turnaround; a named
   backup reviewer.
7. **Root-cause loop.** After each batch, group findings by type (spacing, colour, state, missing
   element). The largest group is fixed once in the LiquidSky theme, not component by component.

## Components with no reference

The component map marks a component `no-reference` when Marobase has nothing to compare it with, and
`partial` when only some of its parts do. Those cannot be reviewed against Storybook until a design
decision is made, and should not sit in the review queue as if they could.

## Review ticket template

```
Reference story:  <Mp* story URL from the component map>
Spec contract:    <deploy>/qa-reference/spec/<component>.json
Implementation:   <LiquidSky story URL>
Themes:           light, dark
States:           <from the spec contract>
Dev self-check:   <pasted assertion output>

Findings: part · expected · actual · screenshot · severity
```
