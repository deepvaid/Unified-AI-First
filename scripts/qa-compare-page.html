LiquidSky design check

How we check that the components developers build match the design, without Figma. Three steps, and this one page.

How it works

  1. Compare

    This page puts the design and the build side by side and lists what differs. It is produced automatically. Nobody writes tests for it.

    Design runs it. The developer reads it and fixes what is listed.

  2. Approve

    The designer reviews the list and the screenshots, and tags anything still open as Blocker, Must-fix or Nice-to-have. With no Blocker left, the component is approved.

    The designer closes the Design Review ticket.

  3. Lock

    QA's Playwright run takes a screenshot of the approved component in the developers' Storybook. That screenshot is the baseline. If the look changes later, the test fails until design approves the change.

    QA adds one line per approved component.
Functional QA does not wait for design review. Both run at the same time.
Only a Blocker holds a release.
TagWhat it meansWhat happens
BlockerThe wrong component, a missing or broken state, or an accessibility failureHolds the release
Must-fixA value differs from the design: size, spacing, colour or typeFixed in the same sprint. QA carries on
Nice-to-haveA matter of taste, or something the design does not coverGoes to the backlog

Checking that a component update does not break a page

Review is component by component, because the same components appear on every page. To make sure an update to one of them does not break a page, QA also keeps screenshots of a few full pages. If a page looks different after a component update, its test fails. A change that was expected is confirmed by design and that page's baseline is saved again. A change that was not expected goes back to the developer.

Who does what

Developer

Before asking for review, open your component in the comparison below and fix what is listed.

Designer

Review from this page. Tag what is left. Approve when no Blocker remains. Confirm page changes that were expected.

QA

Add each approved component to the list in one file, plus a few full pages, and run Playwright. From then on it guards the look.

What QA sets up, once

Baseline screenshots come from the developers' own Storybook, taken on the day design approves. QA needs nothing from design to start. Two small files cover every component: there are no selectors and no per-component tests.

visual.spec.ts
import { test, expect } from '@playwright/test'

// Pages that design has approved. Add one line per approval.
// A page that opens from a button names that button in `open`.
const APPROVED: (string | { id: string; open: string })[] = [
  'components-apppagetitle--default',
  { id: 'components-appdrawerwrapper--default', open: "button:has-text('Open Drawer')" },

  // Full pages. They catch a component update that breaks a page.
  'components-genericindexwrapper--marobase',
  'components-genericindexwrapper--bulk-actions-functionality',
]

const STORYBOOK = process.env.STORYBOOK_URL // the Storybook under test
const THEMES = ['marobaseLight', 'marobaseDark']

for (const entry of APPROVED) {
  const { id, open } = typeof entry === 'string' ? { id: entry, open: undefined } : entry
  for (const theme of THEMES) {
    test(`${id} · ${theme}`, async ({ page }) => {
      await page.goto(`${STORYBOOK}/iframe.html?id=${id}&viewMode=story&globals=theme:${theme}`)
      await page.locator('#storybook-root > *').first().waitFor({ state: 'attached' })
      await page.evaluate(() => document.fonts.ready)
      if (open) await page.locator(open).first().click()
      await expect(page).toHaveScreenshot(`${id}--${theme}.png`, { animations: 'disabled' })
    })
  }
}
playwright.config.ts
import { defineConfig } from '@playwright/test'

export default defineConfig({
  testDir: '.',
  // One folder of approved screenshots, named after the Storybook page.
  snapshotPathTemplate: '{testDir}/baselines/{arg}{ext}',
  use: { viewport: { width: 1280, height: 800 } },
  expect: { toHaveScreenshot: { maxDiffPixelRatio: 0.01 } },
})

Comparison

Each component below shows the design next to the build. The automatic check covers size, spacing, corner radius, colour and type, at rest, in light and dark. Hover, focus and layout are checked by eye from the screenshots. A listed difference is a starting point for the designer, not a verdict.

Questions

Where do the baseline screenshots come from?

From the developers' own Storybook, taken by Playwright on the day design approves a component. Approval is what makes a screenshot a baseline.

Why not use screenshots of the design as the baseline?

The design and the build are two separate codebases. The same component is shown with different sample content and a different frame, so a pixel comparison between them would always fail. That is why the design is compared by numbers and side by side, and the pixel baseline comes from the build itself.

What happens when the design changes later?

The design reference is updated and this page is run again. The change shows up as a new difference. The developer updates the component, design approves it, and QA re-saves that one baseline with the command above.

How do we know a component update did not break a page?

QA keeps screenshots of a few full pages next to the component ones. After any component update the same Playwright run checks them. A page that changed fails, and design decides whether the change was expected.

What about components with no design yet?

They are marked "No design yet" below. They cannot be reviewed for design until a design decision is made, so they should not sit in the review queue. Functional QA on them carries on as normal.

Does this replace functional testing?

No. It only covers how a component looks. Behaviour is tested the way it is today.
